Grouped three levels deep: each big box is a use case (what the robot needs to do), the boxes inside are the files, classes and nodes that do it, and the rows inside those are the functions (or, for Nav2, the plugins and settings this repo configures). 1Mapping

What does the building look like?

Made offline on a workstation: IfcOpenShell needs Python 3.10+, the Jetson has 3.8 and is the slowest machine around. Only the .pgm + .yaml cross over.

ifc_to_map.py

module · workstation

Rasterises only permanent vertical barriers. Slabs and roofs would blank whole rooms; doors and furniture change, so the LiDAR handles them. Door footprints are carved back to free space because many IFC files don't model the wall opening.

  • main(--input, --output, --resolution 0.05, --padding 1.0, --storey, --include-types, --no-clear-doors, --door-padding 0.05)
  • make_geom_settings() → settings (world coords)
  • get_storey_name(element) → storey name
  • project_triangles(model, include_types, storey_name) → yields [(x, y)×3]
  • door_bounding_boxes(model, storey_name, padding) → yields (min_x, min_y, max_x, max_y)
  • rasterise(triangles, resolution, padding, clear_boxes) → (img, origin)
  • write_map(img, origin, resolution, output_prefix) → (pgm_path, yaml_path)

bim_map.pgm + bim_map.yaml

file
  • image, resolution, origin [min_x, min_y, 0], negate 0, occupied_thresh 0.65, free_thresh 0.25

preview_map.py

module · workstation
  • main(--map, --save) → map image with a metre grid, true aspect ratio

map_server

nav2_bringup
  • yaml_filename ← launch arg map
  • publishes /map (OccupancyGrid)

2Sensing

How does robot data reach ROS?

The Go2 publishes on its own network (CycloneDDS, domain 0). Everything else runs on ROS domain 1, so data has to be bridged across.

Go2 robot (built-in sensors)

robot
  • LiDAR → rt/utlidar/cloud_base (PointCloud2_, domain 0, ethrobot)
  • Odometry → /utlidar/robot_odom (Odometry) ⚠ not bridged to domain 1 by anything in the repo

lidar_bridge.py

module · by hand
  • main(): ChannelFactoryInitialize(0, "ethrobot"); ChannelSubscriber(IN_TOPIC, PointCloud2_).Init(on_cloud, 10); pub = create_publisher(PointCloud2, "/utlidar/cloud", SENSOR_DATA)
  • on_cloud(msg: PointCloud2_) → pub.publish(...)
  • to_ros_cloud(msg, PointCloud2, PointField, clock) → PointCloud2

pointcloud_to_laserscan

launched
  • cloud_in ← lidar_cloud_topic (/utlidar/cloud)
  • target_frame base_link, slice 0.05–0.35 mtune
  • publishes /scan (LaserScan), −π…π, 0.15–12 m

3Obstacle sensing

What's in the way that the BIM doesn't know about?

Layers stack top to bottom: the BIM is trusted, the LiDAR adds anything extra, inflation keeps a margin.

global_costmap

nav2_bringup
  • StaticLayer ← /map (BIM walls)
  • ObstacleLayer ← /scan (people, boxes, closed doors)
  • InflationLayer radius 0.4, scale 3.0 → global costmap

local_costmap

nav2_bringup

Rolling 6×6 m window in the odom frame, 10 Hz.

  • ObstacleLayer ← /scan
  • InflationLayer radius 0.4 → local costmap
  • footprint 0.70 × 0.32 m placeholder (both costmaps)tune

4Localization

Where am I on the map?

Odometry drifts; AMCL corrects it by matching the scan to the BIM walls. Lining up the start pose with BIM coordinates is the trickiest part of setup.

odom_to_tf.py

launched

class OdomToTf(Node)

  • __init__(): TransformBroadcaster(self); create_subscription(Odometry, '/utlidar/robot_odom', _on_odom, qos_profile_sensor_data)
  • _on_odom(msg: Odometry) → sendTransform(TransformStamped)
  • main(): rclpy.spin(OdomToTf()) · only if use_odom_to_tf:=true

amcl

nav2_bringup
  • map ← /map
  • scan_topic scan, likelihood_field, 60 beams
  • DifferentialMotionModel ← tf odom → base_link, 500–2000 particles
  • set_initial_pose (0, 0, 0) or RViz /initialposetune
  • publishes tf map → odom, /amcl_pose

6Navigation

How do I get there without hitting anything?

The planner trusts the BIM for the route; the controller dodges whatever the LiDAR sees right now.

bt_navigator

nav2_bringup
  • action server navigate_to_pose (global_frame map)
  • Humble default tree: plan → smooth → follow, recover on failure

planner_server

nav2_bringup
  • GridBased = NavfnPlanner: A*, tolerance 0.5, allow_unknown false

smoother_server

nav2_bringup
  • simple_smoother = SimpleSmoother, max_its 1000

controller_server

nav2_bringup
  • FollowPath = DWBLocalPlanner, 20 Hz, max_vel_x 0.8, max_vel_theta 1.0tune
  • goal_checker: xy 0.20 m, yaw 0.15 rad
  • progress_checker: 0.5 m within 10 s

behavior_server

nav2_bringup
  • spin, backup, wait (max_rotational_vel 1.0)

velocity_smoother

nav2_bringup
  • 20 Hz, max [0.8, 0, 1.0], min [−0.4, 0, −1.0], accel [1.0, 0, 2.0] → /cmd_veltune

7Driving the robot

How do Nav2's commands make the legs move?

Nav2 speaks Twist on /cmd_vel; the Go2 only takes Sport API requests, so the bridge translates and stops the dog if commands go quiet.

cmd_vel_bridge.py

launched

class CmdVelBridge(Node)

  • __init__(): create_publisher(Request, '/api/sport/request', 10); create_subscription(Twist, '/cmd_vel', _on_cmd_vel, 10); create_timer(0.1, _check_watchdog)
  • _on_cmd_vel(msg: Twist)
  • _publish_move(vx, vy, vyaw)
  • _check_watchdog() every 0.1 s
  • _publish_stop()
  • main(): rclpy.spin(CmdVelBridge()); finally _publish_stop()

Go2 sport service

robot
  • Move (api_id 1008): walk at x, y, yaw speed
  • StopMove (api_id 1003)
  • legs move → LiDAR and odometry change

⚠ The bridge publishes on ROS domain 1; the robot usually listens on domain 0. Unverified.

⚠ The firmware has its own obstacle avoidance (SWITCHAVOIDMODE, 2058). Nothing here turns it on or off; decide on purpose whether it runs alongside Nav2.

Before trusting it

Values to tune

  • Footprint in both costmaps is a placeholder (0.70 × 0.32 m). Measure the real Go2.
  • Speed limits: DWB max_vel_x / acc_lim_x and the velocity_smoother limits should match what the Go2 accepts.
  • LiDAR slice: min_height / max_height in the launch file, set for the LiDAR's mounting height.
  • Start pose: initial_pose in nav2_params.yaml, or set it from RViz on a laptop.

Not verified yet

  • Parsing a real IFC file (only synthetic data was tested).
  • The Go2 link: topic names, odometry source, and which DDS domain the sport service listens on.
  • AMCL localizing on a BIM-made map instead of a SLAM map.
  • The Nav2 build from source on Ubuntu 20.04 with Humble.
  • Any of it on the real robot near real obstacles.
